# Vow Protocol — Security Review (2026-11-13)

Scope: `programs/vow/src/**` (≈3,300 lines, 30 instructions), read in full.
Live binary: SHA-256 of the mainnet program (`7ytRMw…yjbJ`, slot 57424019) matches the
pre-fix local build `eb0b2b79…60ef`, so these findings apply to the program running on mainnet.

Live state at review time: 5 identities minted, ~16.0 XNT of shares, reserve holding
0.00089 XNT (rent minimum only) + 16.349 pXNT. Assets ≈ 16.36 XNT vs liabilities ≈ 15.98 XNT, so the protocol is solvent.
X1 Foundation pool fees: sol deposit 0.1%, sol withdrawal 0.1%, referral 0%, epoch fee 4%.

## 1. High: session whitelist bypass (FIXED)

`yield_spend` checked that `calling_program` was executable and on the session's
whitelist, but not that the call **came from** that program. `destination` is unconstrained.
Anyone holding the session key (a leaked dApp key, a prompt-injected AI agent) could send a
top-level `yield_spend` naming a whitelisted program and pay themselves, up to the daily and lifetime caps.

**Reproduced** on a local validator running the exact mainnet binary: the attacker's wallet received 0.1 XNT.

**Fix:** for sessions with a whitelist (`program_count > 0`), `yield_spend` now requires a new
optional account `caller_authority`. It must equal `find_program_address([b"vow_caller"], calling_program)`
and be a signer. Only `calling_program` can sign for that PDA (via `invoke_signed`), so the spend is
proven to arrive by CPI from the whitelisted app. New error: `CallerNotAuthorized` (6036).
Unrestricted sessions (`program_count == 0`) keep the old behavior; see #11.

## 2. Medium: blocked apps could still be paid (FIXED)

`app_registry` was `Option<Account<AppRegistry>>`. The client could pass `None`, which skipped the
`blocked` check, so `block_app` had no effect. It is now a required account pinned by seeds
`["app", calling_program]`. When it is initialized and owned by Vow, the handler deserializes it and
rejects blocked apps. An unregistered app (empty PDA) is still allowed.

Tests: `tests/yield-spend-cpi.test.ts` (9 passing) via `tests/run-yield-spend-tests.sh`, with a
test-only CPI caller in `tests/fixtures/vow-test-caller` (not a workspace member, never deployed).

**Breaking for clients:** `appRegistry` can no longer be `null`, and whitelisted sessions must be spent by CPI.
`frontend/src/DAppDemo.tsx` is updated. Ship the frontend **together with** the program upgrade.

## 3. High: `complete_unstake` haircut is permanent

`complete_unstake.rs`: if `reserve < total_pending_unstake`, it pays
`owed * reserve / total_pending`, closes the escrow, and decrements `total_pending` by the **full** `owed`.
The unpaid remainder is never owed again.

Scenario: A and B each have 100 XNT pending, and the reserve is flushed. A calls
`withdraw_from_pool`, which only tops the reserve up to A's 100 because the gate is `reserve < A.owed`.
A then calls `complete_unstake`: 100 < 200 pending, so A receives **50** and loses 50 permanently.
Even with a single unstaker, the 0.1% pool withdrawal fee leaves `reserve < owed`, so every unstake is
slightly short.

Fix: require `reserve >= lamports_owed` and pay in full or revert. Let `withdraw_from_pool` keep
pulling while `reserve < owed`, with a small buffer for the withdrawal fee.

## 4. High (availability): yield liquidity can be flushed by anyone

`flush_reserve_to_pool` is permissionless and deposits everything above rent. `withdraw_from_pool`
only works with an `UnstakeEscrow`. As a result, `yield_spend` and `withdraw_yield`
(`require!(reserve.lamports() >= amount)`) fail whenever the reserve has been flushed, with no way to refill it.
**This is the state on mainnet right now:** the reserve holds only the rent minimum, so harvested
yield is unspendable. Anyone can also flush a fresh `deposit_yield_balance` before the session spends it.
That directly breaks the agent and session use case.

Fix: flush only `reserve - rent - total_yield_claims - total_pending_unstake (- buffer)`, and
allow a gated pool withdrawal when `reserve < total_yield_claims`.

## 5. Medium: pool fees not accounted

Shares are valued at the pool's `total_lamports / supply`, but converting reserve SOL to pXNT and back
costs 0.1% each way, verified on-chain. Liabilities are overstated by about 0.2% of flushed principal.
Combined with #3, the last unstakers absorb the gap. Current surplus (~0.38 XNT) covers it at today's TVL.

## 6. Medium: config close → anyone can re-initialize as admin

The admin can call `close_protocol_config` at any time. `initialize` has no authority check: whoever
calls it first becomes admin. Re-initializing also zeroes `total_shares`, `total_yield_claims` and
`total_pending_unstake` while VowStates and the reserve persist. A compromised or mistaken admin key,
or a front-run during a "migration", gives someone else full admin control and corrupts the accounting.
Fix: remove `close_protocol_config` (and `set_mint_counter`) from mainnet builds, or require
`initialize` to be signed by the program's upgrade authority. `set_admin` is also one-step with no
acceptance by the new admin (Low).

## 7. Low–Medium: reputation inflation and top-up lock skip

`record_fulfillment` credits the *current* `principal_lamports`. `add_stake` within the same class
keeps `matured = true`. Example: mint 1 XNT, `record_commitment`, wait 30 days, add 99 XNT, then
`record_fulfillment`. Result: fulfilled = 100 vs committed = 1, so `fulfilled_ratio` = 10,000 and the
score is unbounded. The same path lets the 99 XNT top-up be unstaked immediately. This matters if
dApps use `commitment_score` as a reputation signal. Fix: snapshot committed principal in the gate,
cap the ratio at 100, and reset `matured`/`unlock_at` for the added amount (or forbid top-ups after maturity).

## 8. Low: stale share price / just-in-time minting

The config price was 0.99892 vs a pool rate of 1.00072 at review time. Minting before
`update_share_price` gives about 0.18% instant gain that existing holders pay for. New deposits also
sit unflushed in the reserve, earning nothing, but share pool gains. Fix: call `update_share_price`
logic inline in mint, add_stake and activate when a pool is configured.

## 9–12. Informational

- **9.** `pool_referral_fee_account` is unverified. `sol_referral_fee` is 0% today, but if the pool manager
  raises it, any flusher can take the referral cut. Pin it to `reserve_pool_tokens`.
- **10.** No per-owner PDA exists, so one wallet can mint multiple identities. The docs say "exactly one".
- **11.** Unrestricted sessions (`program_count == 0`) can still pay *any* destination up to their caps.
  This is intentional, but AI-agent sessions should always be whitelisted, and the UI should label
  unrestricted sessions as "can pay anyone".
- **12.** `tests/00…06` reference removed instructions and accounts (`resumeProtocol`, `stakePool`,
  `xnftState`), and the `initialize` helper omits `splPool`. The "34 passing" figure isn't reproducible.
  `sdk/src/client.ts` is likewise stale. `Anchor.toml` points `provider.wallet` at the removed
  retired `id.json`. `anchor test` would start a validator on 8899, which is already in use on this host.

# Resolution (same day)

## What changed

| # | Fix |
|---|---|
| 3 | `complete_unstake` pays exactly `lamports_owed` or reverts with `ReserveIlliquid`. The pro-rata branch is gone. |
| 4 | `flush_reserve_to_pool` keeps `rent + total_yield_claims + total_pending_unstake` liquid. `withdraw_from_pool` no longer needs an escrow: it is callable whenever the reserve is short of **any** obligation, and redeems only that shortfall (fee grossed up). `yield_spend` / `withdraw_yield` keep the rent floor. |
| 5, 8 | New `pool_math.rs`: share price = **NAV / shares**. NAV is reserve SOL plus pXNT at the pool rate × (1 − withdrawal fee), minus liabilities. Idle SOL is valued post-round-trip. New stake buys shares at its value net of the 0.1% deposit and 0.1% withdrawal fees, so mint, flush, withdraw, deposit, spend and harvest are all NAV-neutral. `update_share_price` records the pool epoch and fees. Mint, add_stake, activate, harvest, begin_unstake and update_yield_mode revert with `PriceStale` unless the price was refreshed this epoch (clients prepend it in the same transaction). The reserve pXNT account is pinned to its canonical X1 ATA in all three cranks. |
| 6 | `close_protocol_config` removed. `initialize` requires the program upgrade authority. `set_admin` requires the new admin to co-sign. |
| 7 | Every `add_stake` re-locks the position for the (new) class duration. `fulfilled_ratio` is capped at 100. |
| 9 | Referral-fee account pinned to the reserve's own pXNT ATA. |
| 10 | `OwnerIndex ["owner_index", wallet]` is created by `mint_vow`, so a second mint fails. `backfill_owner_index` handles legacy wallets (canonical = oldest identity). Mainnet has 2 wallets holding 2 and 3 identities; those extra identities are grandfathered. |
| 11 | UI warns that an unrestricted session can pay anyone and labels such sessions in the list. |
| 12 | `tests/00–06` replaced by `tests/protocol.test.ts`. `sdk/` (xNFT leftover) replaced by the current Vow SDK via `scripts/sync-idl.sh`. Dead scripts removed. `Anchor.toml` uses `admin.json`, port 28899 and `bind_address 127.0.0.1` (agave 3.0), so `anchor test` works on this host. |

Config layout: the new fields `price_epoch`, `deposit_fee_ppm`, `withdrawal_fee_ppm` and `_reserved` occupy the 32 bytes formerly `merkle_tree`, which was always zero. The account size is unchanged and no migration is needed. After the upgrade those bytes read as "stale" until the first `update_share_price`.

1. `anchor build` and confirm `sha256sum target/deploy/vow.so` matches the tested binary.
2. `anchor deploy --provider.cluster https://rpc.mainnet.x1.xyz --provider.wallet ~/.config/solana/vow-key.json`
3. Immediately run `scripts/update_price_now.ts` (or `daily_crank.ts`). Until then every value-moving instruction fails safely with `PriceStale`.
4. `scripts/backfill-owner-index.ts` (dry run), then `--execute`.
5. `scripts/daily_crank.ts` once: makes the 0.000657 XNT of stranded yield liquid.
6. Deploy the frontend (`set -a; source .env; set +a`, then `npx vercel --prod --token "$VERCEL_TOKEN" …`) and re-alias. Between steps 2 and 6 the old frontend's mint fails (missing `owner_index`), so do it right away.

## Known residuals

- Right after each epoch boundary the stake program rejects withdrawals for a few minutes (`EpochRewardsActive`). Payouts that need pXNT redeemed wait for it. The SDK and crank retry.
- If the X1 pool ever sets a SOL deposit/withdraw authority, flush and withdraw revert (`UnsupportedPoolConfig`). Funds stay safe, and payouts come from liquid SOL only.
- When fresh SOL covers an existing liquidity shortfall, the price can tick up slightly (about 1e-6), because the saved fee accrues to holders. It never goes down for anyone.
- This review and its fixes were done by the same party. Get an independent audit before TVL grows.
