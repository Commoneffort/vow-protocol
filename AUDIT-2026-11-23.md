# Vow Protocol — Security Audit (2026-11-23)

> **Status:** all program findings are fixed and live on X1 mainnet, except H-1 (single upgrade key), which remains an accepted risk. See "Final status" at the end. Sections below record the findings as originally reported.

## Summary

**No finding lets an attacker take staked funds from an identity without a key or signature the attacker should not have.** Accounting is sound: shares and yield balances reconcile exactly on mainnet, and a full-exit simulation paid every identity its exact fixed amount.

The largest risk is operational: one hot key can upgrade the program, and so controls all funds. The most serious program bug is that authority profiles silently create unrestricted sessions. No profile exists on mainnet yet, so nobody is affected today.

## High

### H-1: One key controls the whole protocol

`BPmZB128…KV8M` is both the upgrade authority and the protocol admin, as anyone can verify on-chain. Whoever controls an upgrade authority can replace the program, so users must trust this single key.

**Recommendation:** move the upgrade authority and admin to a multisig, ideally with a timelock, before TVL grows.

### H-2: Authority profile whitelist is ignored

`create_session.rs:73-85` inherits daily limit, lifetime limit, and expiry from a profile, but never reads `default_allowed_program_ids`. An empty `allowed_program_ids` argument gives `program_count = 0`, which means unrestricted.

**Reproduced:** a profile allowing one program produced a session with `program_count = 0`, and the session key paid 0.5 XNT directly to its own address.

**Impact:** a user who relies on a profile to restrict an agent gets a key that can pay anyone, up to the limits. There are no profiles on mainnet, and the frontend and SDK do not use them, so exposure is currently zero.

**Fix:** when a profile is supplied and the argument list is empty, copy the profile's list.

```rust
let programs: Vec<Pubkey> = match &ctx.accounts.authority_profile {
    Some(p) if allowed_program_ids.is_empty() =>
        p.default_allowed_program_ids[..p.program_count as usize].to_vec(),
    _ => allowed_program_ids,
};
```

## Medium

### M-1: Recoverable session keys can be phished

The key is `SHA-256(signMessage(text))`. The text contains `Domain: <origin>`, but the wallet does not enforce that value. A malicious site can request a signature over the exact text for the real domain and rebuild the key. The previous documentation said this prevented cross-site theft, which was wrong.

**Impact:** the attacker gets that session's spending power, and the UI defaults to no spend cap. Recoverable mode is the default.

**Fix:** adopt Sign-In-With-Solana style signing if the wallet verifies domains. Otherwise, default to random keys and make recovery opt-in. Default new sessions to a whitelist and a cap. The UI and docs now warn users.

### M-2: Recovered principal becomes session-spendable yield

`harvest` resets a negative gain to zero. If the price later recovers, the recovery counts as new gain. Harvest is permissionless, so a session-key holder can trigger it at the low and again after recovery.

**Reproduced:** with 10 XNT staked, the price moved 1.0 → 0.5 → 1.0. Net change was 0%, but 5 XNT became `yield_balance` and the session spent it, leaving a position worth 5 XNT. The proof used the testnet price instruction to simulate the move, and session limits still apply.

**Fix:** carry negative gain forward instead of resetting it, so only value above the previous high is harvestable.

```rust
if gain <= 0 { (0u64, 0u128) } // leave accrued_gain unchanged
```

### M-3: Anyone can permanently freeze a commitment record

`record_commitment` and `record_fulfillment` are permissionless and one-time per identity.

**Reproduced:** a third party recorded a 1 XNT identity. After it grew to 1,001 XNT (class 4), the record stayed at class 0 and 1 XNT, and the owner's correction was rejected.

**Fix:** require the owner's signature, or make records updatable from current state. Until then, dApps should not gate on `commitment_score`; the docs now say so.

### M-4: Session secrets in localStorage under a weak CSP

Session private keys are stored unencrypted in localStorage. The live CSP allows `'unsafe-inline'` and `'unsafe-eval'` in `script-src`, which removes most of its protection against injected scripts. No XSS was found.

**Fix:** remove both directives and test the build, and drop `fonts.googleapis.com` from `script-src`. Consider non-extractable WebCrypto keys for wrapping session secrets.

### M-5: Deposit can target another wallet's identity

`lastVowState` is restored from localStorage and is not cleared on an account switch if the new wallet has no saved identity. "Top Up" falls back to it, and `deposit_yield_balance` accepts any identity. Wallet B can therefore send XNT to wallet A's identity, and only A can withdraw it.

**Fix:** clear identity state on wallet change, and confirm before depositing to an identity the wallet does not own. The UI currently shows a warning only.

### M-6: Insolvency halt does not stop first-come payouts

Insolvency halts freshness-gated instructions, but `yield_spend`, `withdraw_yield`, and `complete_unstake` continue. After a severe pool loss, the first claimants could be paid in full and later ones could not.

**Fix:** decide the policy explicitly. A persistent insolvency flag with pro-rata settlement is the fair option.

### M-7: Deployed frontend is not reproducible

`frontend/`, `vercel.json`, and `.vercelignore` are git-ignored, so the code users sign transactions through has no history or review trail. The Vercel build also uses `npm install` rather than `npm ci`.

**Fix:** track these files (without secrets) and switch to `npm ci`.

### M-8: Superseded deployment credential

A superseded hosting credential remained in local operator notes. It was never in git history. It has been revoked by the owner and removed from those notes.

## Low

- **L-1: `block_app` and unrestricted sessions.** The key can name any executable as `calling_program`. Naming the blocked app reverted, but naming the System Program paid out. Document this as the intended scope, or block by destination.
- **L-2: Same-second invalidation.** `yield_spend` uses `start_ts >= sessions_invalidated_at`. A session created in the same transaction before `complete_unstake` + `activate_stake` remained spendable. Use a per-cycle epoch counter rather than a timestamp.
- **L-3: Zero-day profile expiry.** A profile with `default_expiry_days = 0` produces `expiry_ts == start_ts`, so the session is expired on creation. Treat 0 as no expiry or reject it.
- **L-4: Stale `accrued_gain`.** `begin_unstake` does not clear it, so a later Treasury harvest reverts with `SharesUnderflow`. Payouts are unaffected. Zero it in `begin_unstake`.
- **L-5: Surplus after full exit.** With zero shares, the price resets to the pool rate. The next depositor receives any leftover surplus, up to the 1.25× cap. Sweep or retain a minimum share supply.
- **L-6: `set_mint_counter`.** It is still callable on mainnet although its migration purpose has passed. It can only skip mint indices. Gate it to testnet or remove it.
- **L-7: Dependencies.** `npm audit` reports 113 advisories (2 critical, 35 high). Most come through `@solana/wallet-adapter-*`, which no frontend source file imports. Remove those packages and re-audit.
- **L-8: Fork test.** `tests/mainnet-fork.test.ts` assumes all live identities are matured, so it now fails with `NotMatured`. Expire locks in the snapshot, as this audit did in a scratch copy.
- **L-9: Dead code.** `close_config.rs` and `initialize_tree.rs` are not compiled, and scoring constants are unused. Remove them so a future change cannot re-enable them by accident.

## Trust assumptions

- The reserve PDA signs CPIs into the X1 stake pool program `XPoo1Fx6…CZux`, which is **upgradeable by `2sXr5THr5ZAwSfuJAc1KogPKZ2uKkhfNUAtEvNw5Q6Z7`**. A malicious or compromised upgrade there could affect funds in the reserve's position.
- Yield and pricing depend on the X1 Foundation updating the pool each epoch. If it lags, value-moving instructions wait.
- The program parses the pool account at fixed offsets. A pool layout change could break pricing until the program is upgraded.

## Reviewed with no issue found

- Account validation: PDA seeds, ownership checks, and `has_one` on owner instructions.
- Soulbound guarantees: no instruction changes `owner` or closes `VowState`.
- Whitelisted `yield_spend` CPI proof through the `vow_caller` PDA.
- Pool CPI account pinning, including the canonical pXNT ATA and referral account.
- Flush and withdraw liquidity rules, and NAV neutrality of mint, flush, withdraw, and spend.
- Share-inflation cap (the prior attack is still blocked on today's state).
- `initialize` and `set_admin` authority checks, and testnet-only gating of `dev_*`.
- Full exit on a fork of today's state: all 6 identities were paid their exact fixed amounts.

# Re-audit after the mainnet upgrade (2026-11-23)

**Result:** no finding allows direct theft of funds, and all earlier program fixes are confirmed live. The re-audit found **3 new Medium issues, all in the insolvency pause added by the M-6 fix**. R-1 to R-3 were then fixed and deployed (see "Final status").

## Verified

- Mainnet binary matches the tested build: `5dd7623e…0b81`, slot 95347754.
- Unit 7/7, local 27/27, mainnet fork 10/10 on today's state, including the 1 XNT top-up at 15:04 UTC.
- Share and yield totals reconcile exactly with the per-identity sums.
- `x1vow.xyz`: valid certificate, TLS 1.0/1.1 rejected, 7 security headers, path traversal and dotfiles blocked, write methods rejected, no source maps or secrets in the published site.
- No secret patterns in files tracked or eligible for commit.

## New findings

| ID | Severity | Finding | Evidence |
|---|---|---|---|
| R-1 | Medium | The pause only starts when someone runs `update_share_price`, so a claimant can withdraw first after a loss | **Reproduced on fork** |
| R-2 | Medium | `deposit_yield_balance` still accepts funds while payouts are paused, trapping the deposit | **Reproduced on fork** |
| R-3 | Medium | A stake pool fee change can pause all payouts while the reserve is short, even for fully liquid claims | **Reproduced on fork** |
| R-4 | Low | Demo creates a real unrestricted mainnet session and its stored key is not per-wallet | Code review |
| R-5 | Low | Site publishing is not separated into a dedicated deploy user | Verified |
| R-6 | Low | Google Fonts is a third-party stylesheet dependency | Verified |
| R-7 | Info | 405 responses omit security headers; they have no meaningful body | Verified |

**Recommended fixes**

- **R-1:** have `yield_spend`, `withdraw_yield`, and `complete_unstake` require a price refreshed this epoch, so a new epoch's loss is seen before any payout. Clients prepend the update.
- **R-2:** reject `deposit_yield_balance` while `config.insolvent` is set.
- **R-3:** judge solvency using the pool's current redemption value without scheduled fees, and keep the pause for real asset shortfalls. A sharp fee change should stop new value-moving actions without freezing claims already backed by liquid SOL.
- **R-4:** remove the demo's mainnet write path or use a whitelisted demo program.
- **R-5:** publish from a separate deploy user.
- **R-6:** self-host the font and remove Google from the CSP.
